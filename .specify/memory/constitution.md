# Конституція Lefleat

## Основні принципи

### I. Тонка точка входу

Файл `index.ts` МУСИТЬ містити лише імпорти ES6 та мінімальний виклик ініціалізації. У файлі входу заборонено розміщувати логіку додатку, обробники подій чи сервісний код.

- `index.ts` — єдина точка входу браузерного додатку.
- Уся функціональність МУСИТЬ знаходитися в іменованих модулях (наприклад, `map-init.ts`, `layers.ts`, `ui.ts`, `state.ts`).
- Обґрунтування: тонка точка входу робить структуру додатку одразу зрозумілою і не дає файлу входу перетворитися на неконтрольоване сховище нерелевантної логіки.

### II. Модульна архітектура

Кожна функціональна відповідальність МУСИТЬ розміщуватися в окремому модулі; дублювання між модулями заборонене.

- Приклади поточних модулів: ініціалізація карти, керування шарами, UI-компоненти, обробка об’єктів, контрол малювання, трансформація overlay, утиліти, стан.
- Модулі МУСЯТЬ використовувати `import`/`export` ES6; для внутрішніх імпортів обов’язкові відносні шляхи.
- Циклічні залежності МУСЯТЬ бути усунені, а не потерпілими.
- Обґрунтування: виділені модулі локалізують зміни, зменшують конфлікти злиття і роблять модульне тестування можливим.

### III. TypeScript-дисципліна (НЕПОРУШНО)

Уесь вихідний код МУСИТЬ бути типізованим TypeScript. Тип `any` МОЖЕ використовуватися лише тоді, коли типізована альтернатива неможлива, і його застосування МУСИТЬ бути задокументоване коротким коментарем українською мовою.

- Інтерфейси МУСЯТЬ визначати форму доменних об’єктів і спільного стану.
- Новий код МУСИТЬ використовувати конкретні типи; використання `any` у новому коді заборонене без виняткового обґрунтування.
- Увесь новий код МУСИТЬ проходити `npm run lint` і `npm run check-rules` без помилок.
- Обґрунтування: сувора типізація виявляє помилки форми даних на етапі збірки, що критично для геометрично-навантаженого додатку, який оперує координатами, об’єктами карти й серіалізованим сховищем.

### IV. Безпека даних, валідація та зворотна сумісність

Lefleat зберігає роботу користувача в `localStorage` і підтримує імпорт/експорт JSON, GeoJSON та KMZ. Усі збережені та імпортовані дані МУСЯТЬ бути валідовані, процедури імпорту МУСЯТЬ підтримувати щонайменше одну попередню версію формату експорту, а будь-який користувацький вміст, що рендериться як HTML, МУСИТЬ бути санітизованим або генеруватися через `textContent`.

- Ключі `localStorage` МУСЯТЬ використовувати префікс `lefleat_`.
- Розпарсені дані МУСЯТЬ бути валідовані перед заміною внутрішнього стану; про недійсні файли МУСИТЬ повідомлятися користувачеві зрозумілим повідомленням замість аварійного завершення додатку.
- Використання `innerHTML` із несанітизованим користувацьким вводом заборонене; для динамічного HTML МУСИТЬ використовуватися санітизація (наприклад, DOMPurify) або безпечний шаблонізатор.
- Усі файлові імпорти МУСЯТЬ валідуватися за MIME-типом/розширенням і перевірками коректності вмісту.
- Обґрунтування: користувачі покладаються на карту для збереження реальної роботи; тихе пошкодження даних або порушення формату руйнує довіру. Картографічний інструмент із імпортованими overlay і власними мітками є природною мішенню для ін’єкцій; захисні налаштування за замовчуванням захищають користувачів без постійного ручного контролю.

### V. Користувацько-орієнтований UI, безпека та інклюзивність

UI-взаємодії МУСИТЬ бути дружніми до клавіатури, інформативними, безпечними за замовчуванням та доступними.

- Модальні діалоги МУСЯТЬ закриватися клавішею Escape і утримувати фокус під час активності (focus trap).
- Користувацький вміст МУСИТЬ рендеритися через `textContent` або санітизований HTML; сирий `innerHTML` з несанітизованим вводом заборонений.
- Іконки та зображення, що несуть семантичне навантаження, МУСЯТЬ мати текстові альтернативи (`aria-label`, прихований текст або `title`) для користувачів зі скринрідерами.
- Обґрунтування: безпечні та доступні інтерфейси зменшують ризик ін’єкцій і роблять інструмент корисним для ширшої аудиторії, включаючи людей із вадами зору.

### VI. Якість, тестування та інфраструктура

Критична логіка МУСИТЬ бути покрита автоматичними тестами, а зміни МУСЯТЬ проходити ворота якості перед злиттям.

- Кожен новий функціональний блок МУСИТЬ супроводжуватися тестами, якщо він містить обчислення геометрії, серіалізацію даних, валідацію вводу або публічний API модуля.
- Перед комітом МУСИТЬ виконуватися `npm run lint` і `npm run format`; перед вважанням функціоналу завершеним — `npm run check-rules`.
- Проєкт МУСИТЬ підтримувати CI-перевірку (GitHub Actions або еквівалент), що запускає `npm run check-rules` та тести на кожному pull request’і.
- Обґрунтування: тести та CI запобігають регресіям у форматах даних і геометричних обчисленнях, а ворота якості зберігають єдиний стиль коду в команді.

## Технологічні обмеження

### Стек

- **Frontend**: TypeScript 5.x, ES6 модулі, Leaflet.js для інтерактивних карт, Material Icons для іконографії.
- **Збірка**: `tsc` для компіляції; ESLint із `@typescript-eslint`; Prettier для форматування.
- **Сховище**: браузерний `localStorage` для автоматичного збереження; JSON/GeoJSON/KMZ для обміну даними.
- **Стилізація**: звичайний CSS із Grid і Flexbox; наразі не потрібна залежність від зовнішнього CSS-фреймворку.

### Правила файлів і модулів

- Назви файлів використовують `camelCase.ts`.
- `index.ts` залишається єдиною точкою входу верхнього рівня.
- Дебаг-скрипти та експерименти МУСЯТЬ розміщуватися в `del/` із префіксом `debug-` і НЕ МУСЯТЬ імпортуватися продакшен-кодом.

### Стиль коду

- Коментарі пишуться українською мовою.
- Консольні логи використовують емодзі-префікси (`🚀`, `⚠️`, `❌`, `✅`) і групуються за функціональністю.
- Продакшен-збірки НЕ МАЮТЬ містити надмірної кількості дебаг-логів.

## Робочий процес

### Ворота якості

1. Перед комітом виконати `npm run lint` і `npm run format`.
2. Перед вважанням функціоналу завершеним виконати `npm run check-rules`.
3. Для UI-змін очікується ручна перевірка на різних розмірах екрана.
4. Для змін, що зачіпають критичну логіку (геометрія, серіалізація, валідація), додати або оновити автоматичні тести.

### Очікування щодо рев’ю

- Кожна зміна МУСИТЬ бути прослідковуваною до функціональної відповідальності або задокументованого виправлення помилки.
- Нові модулі МУСЯТЬ відповідати наявній модульній структурі та НЕ МУСЯТЬ дублювати наявні утиліти.
- Складність має бути обґрунтованою; надавайте перевагу простішим рішенням, які задовольняють поточну функцію, над спекулятивними абстракціями.

### Дебагінг і експерименти

- Дебаг-файли МУСЯТЬ залишатися в `del/`.
- Жоден продакшен-код не може залежати від файлів у `del/`.

## Управління

Ця конституція є найвищим керівним документом для Lefleat і має перевагу над випадковими правилами або вбудованими коментарями, якщо вони суперечать їй.

- **Внесення змін**: будь-яка зміна цього файлу вимагає оновлення версії згідно з Semantic Versioning, фіксації обґрунтування та поширення зміни на `RULES.md`, `README.md` й артефакти `.specify/templates/`, якщо вони зачеплені.
- **Версіонування**: MAJOR — для несумісних перевизначень або вилучень принципів; MINOR — для нових принципів/розділів або суттєво розширеного керівництва; PATCH — для уточнень, редакцій, виправлення опечаток.
- **Відповідність**: усі pull request’и та плани функцій МУСЯТЬ перевіряти відповідність поточній конституції. Розділ `Constitution Check` кожного плану реалізації МУСИТЬ перелічувати ворота, виведені з цих принципів.
- **Перегляд**: конституцію МУСИТЬ переглядати не рідше ніж раз на квартал або після суттєвої зміни архітектури чи стеку.
